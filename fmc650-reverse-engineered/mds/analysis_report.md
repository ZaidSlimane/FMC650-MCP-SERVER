## 2. New evidence produced here

### 2.1 Generator id formula (from CIL, not inference)

`Configuration.Generator.Utilities.PropertyIdCalulator.CalculatePropertyId`
body:

```
ldarg.2 ; startId
ldarg.3 ; offset
ldarg.1 ; offsetMultiplier
mul
add
ldarg.0 ; orderId
add
ret
```

→ **`id = startId + offsetMultiplier * blockIndex + orderId`**

This is the arithmetic behind `<Geozones StartId Offset Count>` and
`<Polygon StartId Offset PointsCount>`; `<ListConfiguration StartId
NumberOfItems>` is the degenerate `offsetMultiplier = 1` case.

### 2.2 Cfg compression is not reproducible from stock libraries

All zlib levels, `Z_FILTERED`, .NET `GZipStream`, and bundled SharpZipLib 1–9
were tried: closest is SharpZipLib level 5 at 27,423 B vs the vendor's 27,370 B,
and the gzip OS byte differs (vendor `0x0A`, SharpZipLib `0xFF`). Conclusion:
**text payload is the byte-exact contract**; container bytes are vendor-compressor
specific and irrelevant to a device upload.

## 3. The 6,451 unattributed ids are six structural families

All unknown ids fall in these blocks — no long random tails:

| Range | Unknown ids | Shape |
| --- | --- | --- |
| 45,000–54,999 | 2,183 | repeated 6-wide groups every 10 (`45100…45105`, `45110…45115`, …) |
| 74,000–74,999 | 57 | small table |
| 90,000–90,999 | 359 | table |
| 103,000–108,999 | 2,515 | five ~500-wide blocks |
| 150,000–151,999 | 788 | two blocks |
| 180,000–181,999 | 549 | two blocks |

They are generated by the Configurator's runtime property model
(`FMB.Core.Factory.PropertyVault.GenerateProperty`,
`PropertyObjectCreator`, and the `IOItem`/`IOTemplate` expansion), not by any
literal id in the XML. The same families explain the `45xxx` six-wide groups and
the `10xxxx` blocks seen in the sample.

## 4. What is required to finish

1. **Branch selection.** Drive `Configuration.Generator.ConfigurationProvider`
   (`GenerateConfiguration(HardwareVersion, string, Version, IEnumerable<int>,
   string, HardwareInformation, int, string)`) with the real DI graph so the
   vendor itself resolves `Hardware`/`Software`/`Spec` gating for
   `FMC650:1 / SpecId 1 / 4.43.01.0`. The interfaces it needs
   (`IExtensionsService`, `IBaseExtensionFactory`, `IConfigurationCompiler`,
   `IConfigurationVariationGenerator`, `IConfigurationParser`,
   `IConfigurationValidation`, `IConfigurationFamilyCreator`) are all present in
   `bundle_extract/`; the missing piece is the composition root, not the logic.
2. **Runtime property generation.** Reimplement or invoke `PropertyVault` /
   `PropertyObjectCreator` to obtain the six families above with names, types,
   min/max/defaults, then diff against the cfg id set until coverage is 100%.
3. **Validation across cfgs.** With a second, non-default cfg (different zones,
   IO enabled), confirm geozone/polygon/list block counts and that the id set is
   invariant for a given firmware/hardware/spec.
4. **Optional:** parse `fw_image.bin` for a parameter descriptor table. It is
   not gzip and starts with a little-endian int table; nothing yet proves it
   contains parameter metadata, so this is a lower-confidence path than (1)+(2).


## 6. Generator driver — progress made after the earlier session

The composition root the previous session could not find was located:
`Configuration.Generator.Factories.ConfigurationProviderFactory` (8-argument ctor,
`Create()`). The full offline graph now constructs and runs:

```
XElementParser
SpecFactory / HardwareFactory / SoftwareFactory / BaseExtensionFactory
ConfigurationFilter + ConfigurationMapper + ConfigurationVariationInheritor
ConfigurationVariationGenerator + ConfigurationParser + ConfigurationFormatter
ConfigurationCompiler + ConfigurationValidation + ConfigurationFamilyCreator
ConfigurationProviderFactory(...).Create()
```

Two practical findings from running it:

1. **Key store blocks offline use.** `ExtensionsService.RefreshKeys()` null-references
   without a registered vendor account, and `RegisterUser()`/`Provide()` hang on
   network. `IConfigurationSettings` is only two properties, so it is replaced by a
   local implementation and `IExtensionsService` by a permissive stub
   (`CanUse(id) => valid key`). The driver in `../tools/ximgen/` contains both.
2. **Family layout matters.** `FamilySettings` derives the family from the directory
   name and expects `FMB640/Base.xml`, `BaseExtension.xml`, `Lists.xml`,
   `Collections.xml`, `Hardware.xml`, `Templates.xml`, `Specs.<id>.xml`. The branded
   resource names must be renamed accordingly.

`GenerateConfiguration(HardwareVersion hardwareVersion, string fmType, Version
softwareVersion, IEnumerable<int> featureSet, string familyName,
HardwareInformation hardwareInformation, int specId, string specCustomer)` is
reached and executes the real compiler. Current failure, with the exact contract:

```
InvalidConfigurationException: Unable to find spec id(1001) configuration file
  at SpecFactory.BuildSpecs(ICollection<XElement> specElements, List<SpecFile> specFiles)
```

`specFiles` must be `List<SpecFile>` built by the vendor's own loader (Id parsed from
the `Id` attribute, patch number from `PatchNo`), not a list of paths. That loader is
the single remaining integration step; the compiler itself is already running.

## 5. Non-negotiables for the final artifact

- Every id must state its provenance and confidence; no invented labels.
- The cfg writer must keep the exact id set, ascending order, header order and
  the continuation quirk; only values may change.
- Completeness is proven by id-set equality with a real export, not by row count.

## 7. Generator breakthrough (this session) — and what it did not buy

The vendor compiler was finally made to run end-to-end offline. Output is checked
in as `generated_FMC650_spec1_cfg4.43.1.0.xml` (1.4 MB) with its id list in
`generated_FMC650_spec1_cfg4.43.1.0_ids.txt`.

Command:

```
BUNDLE_DIR=.../bundle_extract BRAND_DIR=.../brand/FMB640 dotnet run -c Release   # tools/ximgen
```

Result of `GenerateConfiguration(FMC650:1, "FMC650", 4.43.1.0, specId 1)`:

```
GENERATED elements=18139 ids=1150
GEN 1150   CFG 11688   overlap 1149   gen-only 1   cfg-only 6451
```

Two findings that made it work, both discovered by measurement rather than reading:

1. `FamilySettings` must receive **absolute** paths whose basenames match the vendor
   resource names; passing bare resource ids makes the loader open them relative to
   the process CWD (hence the earlier `.../gen/1000` error).
2. Spec references (`<Spec Id="1001" PatchNo="1"/>`) exist only in the **BaseExtension**
   software branches. For `SpecId 1` they are irrelevant, and stripping them removes
   the `SpecFactory.BuildSpecs` dependency entirely. That is what unblocked generation.
   (`SpecFile` itself is trivial: `SpecFile(int id)` with read-only `Id` and `Patches`.)

### Why 6,451 ids remain, stated precisely

The unknown set is entirely *expanded* parameters. `<ListConfiguration>` has
`StartId`/`NumberOfItems` but **no `Offset` attribute** (`grep -c Offset= FMB640.Lists.xml`
→ 0), so list ids are contiguous and already accounted for. The remaining ids live in
block-allocated families:

```
40k–54k   3,578      100k–108k  2,515
150k–151k   790      180k–181k    549
90k         359      70k           57
```

Naive `StartId..StartId+NumberOfItems` ranges from the generated doc cover only
1,186 of the 6451. Each list/IO item therefore reserves a block of
`offsetMultiplier` ids and addresses fields by `orderId` — the
`id = startId + offsetMultiplier*blockIndex + orderId` rule already recovered from
`PropertyIdCalulator`. The `offsetMultiplier` per definition is exactly what the
still-unparsed `PropertyVault`/`IOItem` layer supplies, so that is the next target,
not the compiler.

**Honest status: the compiler is solved; the expansion model is not.**

## 8. IOItem block expansion — the residual explained, schema closed

`PropertyVault` was a red herring: the expansion is compile-time metadata. The
generated document carries 1,208 `IOItem` nodes; all 150 vendor XML files together
carry `IoId` on 3,368 `IOItem` elements, 2,445 unique bases (the compiler emits only
the subset visible for this hardware, so the XML set is the one to use).

Measured rule:

```
id = IoId + order,   order in 0..5        (six cfg fields per IO item)
```

Evidence, all from the reference cfg rather than from source reading:

- offset histogram from each base: 0–5 present for every base (the 0–4 offsets hit
  520/520/407/407/520 times), offsets 6–9 only via the *next* base, because bases are
  spaced 10 apart (`50000, 50010, 50020, …`);
- the last 109 unattributed ids were all exactly `base + 5`, which is what fixed the
  width at 6 rather than 5;
- `<Geozones StartId="20100" Offset="20" Count="100">` and
  `<Polygon StartId="60310" Offset="20" PointsCount="8">` show the same
  `startId + offset*index + order` shape. Across the document only 72 `Offset=`
  attributes exist: 70 are `<Operand Offset="4">` (expression operands, not ids).

`ListConfiguration` starts (1,600 / 4,000 / 5,000 / 5,500 / 6,000 / 8,000 …) have no
`Offset` and are contiguous, which is why `StartId..StartId+NumberOfItems-1` already
covered them.

## 11. Practical path forward — generating a `.cfg` without the vendor UI

Short answer carried over from the mission review, refined by measurement:
**partially possible today.** The format, the parameter map and the
vendor generator are in hand; the device-side validation logic is not.

2. **Parameter map** — `fmx65_03.01.01.Rev.15_schema.json`: label, type, unit, default, min/max,

### Corrected practical path

The review's sketch missed one hard rule that the artifacts *do* encode:
**the device rejects a cfg whose id set does not match its firmware/hardware/spec**.
A "partial config" with only understood ids is therefore not a valid unit of
exchange. The working recipe:

0. **Anchor the id set on a vendor-exported cfg** (e.g.
   `cfgs/device_export_original.cfg`, 11,688 ids). Never derive the id set from the schema alone — the schema is a
   superset across hardware/spec branches (13,966 ≠ 11,688 by design).
1. Optionally run `ximgen` to obtain the compiled document for default values.
2. Change only **values**, looking each one up in
   `fmx65_03.01.01.Rev.15_schema.json` and
   checking it against every constraint that row encodes (type, min/max,
   regex, collection, max-length).
3. Rebuild text with `cfg_tool.py write`; header keys/order fixed.
4. Gzip (`mtime 0`); on-device acceptance of our container bytes is
   **unverified** — the vendor's gzip byte stream was not reproduced.

For values with no encoded constraint (the 69.3 %), copy the known-good
reference value and change it conservatively, or resolve the real constraint by:

- **IL work** in the vendor DLLs (the Configurator has per-parameter positive/
  negative value callbacks — see `FMB.Core` `ValidValueCallback` backing fields),
- **corpus inference** — collect more device configs and learn accepted ranges
  empirically (the instrumented-attribution idea in §4 still applies),
- **defaults-only edits** for the parameters not understood.

The format is solved. The parameter set is solved. **The value-constraint
enforcement that the Configurator performs live is the remaining risk layer,
and it is quantified above rather than assumed away.**

§11 in practice — `tools/make_cfg.py` implements the recipe as one command:
anchored id set (copied, then asserted-invariant after the edits), schema
validation per edit (type/min/max/regex/max-length — `FAIL` refuses; unconstrained
rows edit with a loud `WARN`), header passthrough, deterministic gzip. Demo on
the reference cfg: 3 APN edits accepted and round-tripped; over-length APN and
`48100=999999` (> max 300) refused. Output: `cfgs/my_solid_upload_test.cfg`
(shipped in this folder), 11,688 params, 99,181 B text payload.

**Live observation during the device test (to resolve):** the connected device
reports configuration model **4.41.0.0** while Configurator-saved files carry
